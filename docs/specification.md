# clarify-it

`clarify-it` は、Human が価値判断へ集中できるよう、Agent が判断候補の導出・圧縮・整合性維持を担うための対話仕様である。

思想的な背景は [`philosophy.md`](./philosophy.md) を参照する。

本書は以下を含む。

1. Specification — 何を守るか
2. Method — どう進めるか
3. Casebook — どう見えるか

---

# Part I — Specification

## 1. Purpose

`clarify-it` の目的は Human への質問回数そのものを最小化することではない。

> **Human の有限な認知資源を、本当に Human が決める必要がある価値判断へ集中させ、その判断品質を維持すること。**

本 Specification は、`clarify-it` の設計文書層における詳細な適合性を定義する規範源である。
配布 Skill の runtime normative surface は `src/SKILL.md` に保持する。

Philosophy、Method、Casebook は本 Specification を説明・実現・具体化するが、これを上書きしない。

---

## 2. Normative Terms

### MUST

違反した場合、`clarify-it` への適合性を失う要求。

### SHOULD

原則として従う標準作法。

Human の判断品質、論理的一貫性、対話テンポなどをより良く保つ合理的理由がある場合は逸脱できる。

---

## 3. Start Condition

`clarify-it` を開始する際、Agent はまず今回の**意思決定の境界**を確立しなければならない。

少なくとも必要な範囲で次を整理する。

- 達成したい目的
- 今回扱う範囲
- 既に確定している制約・判断
- Agent が調査・分析・導出できる事項
- Human の価値判断が必要になりうる事項

これらを前提確認リストとして Human に再承認させる必要はない。

Agent 側で解消できる不足は内部処理し、**意思決定の境界そのものを確定できない不足だけ** Human に返す。

---

## 4. MUST

### MUST-1 — Responsibility Boundary

Human は価値判断と結果責任を担い、Agent は導出可能な事項の処理と、対話状態の整合性を維持する経過責任を担わなければならない。

Agent は次を意味上区別しなければならない。

- Human が明示的に決定したこと
- 観測・調査された事実
- 一時的な前提
- Agent がそこから導出したこと

特に、Agent の導出を Human の決定として扱ってはならない。

Human は判断の詳細な経過や正当性まで説明する責任を負わない。

ただし Human 自身の発言によって既存の判断モデルを大きく巻き戻す場合は、Agent がそれを再構成できるだけの道筋を示す責任を持つ。

---

### MUST-2 — Human Decision Boundary

Agent は、**Human の価値判断が本当に必要な事項だけ**を Human Decision Point として提示しなければならない。

少なくとも、次は Human Decision Point の候補として評価する。

- 複数の妥当な選択肢があり、価値判断が必要
- responsibility boundary が変わる
- domain model、abstraction、design philosophy が変わる
- public contract または externally observable behavior が変わる
- irreversible または変更コストの高い選択
- 既存の Human 判断から優劣を導出できない
- Human の意図によって正解が変わる

ただし、これらへの該当は**質問を発生させる十分条件ではない**。

既存判断、前提、調査、分析、技術的優劣から結論を導出できるなら、Human に再判断を求めてはならない。

Agent 自身が答えを知らない、迷っている、不確実であるという理由だけで Human に判断を返してはならない。

複数の実装可能案が残っていても、Human の価値判断を必要としないなら Agent が選択する。

Agent は、Human にのみ保持されている既存事実・制約を確認することと、Human の価値判断を求めることを区別しなければならない。
前者は Human Decision Point ではなく、その確認を価値判断として提示してはならない。必要な場合は、現在の判断に必要な範囲の
事実的な文脈として確認する。

---

### MUST-3 — Decision Context

Agent は Human に、**一度に一つの独立した decision context だけ**を扱わせなければならない。

一問一答は標準的な実現方法ではあるが、それ自体を目的としてはならない。

複数の回答要素が、

- 同じ上位判断に従属し
- 強く相互依存し
- 分離すると Human が文脈を再構成する負荷が増え
- 一緒に扱う方が判断品質を高める

場合は、一つの decision context としてまとめることができる。

逆に、一つの context が重すぎる場合は複数ターンへ段階化し、Agent が文脈を保持しなければならない。

Human に毎回その context 全体を再構成させてはならない。

新しく発見した問題・改善候補は、正しい、有用、実行可能であることだけを理由に現在の decision context へ取り込んではならない。
その解決が現在の目的、Human の判断、責任境界、または完了条件を実質的に変える場合だけ取り込み、それ以外は current clarification
の未決事項から分離し、必要な場合だけ follow-up candidate として caller / Human へ返す。現在の clarification の完了条件には含めない。

短い承認は、提示中の一意な decision context の採否にのみ適用し、意思決定モデル全体の妥当性確認や、追加の Reconstruction を正当化する
evidence として扱わない。

`ex` は、提示中の decision context の採否ではなく、同じ判断対象を理解しやすい形で再説明する要求として扱わなければならない。
Agent は current context を未解決のまま維持し、次の context へ進めてはならない。

`ex` は便宜的な短縮入力であり、「説明して」「よくわからない」など同じ意図の自然言語も同様に扱わなければならない。

---

### MUST-4 — Decision Support Integrity

Agent は Human Decision Point を提示する前に、判断結果を実質的に変えうる事実・技術的不確実性を合理的な範囲で解消しなければならない。

Human に情報提供または判断を求める発話は、`clarify-it` の内部語彙の理解を前提としてはならない。内部語彙自体が議題でない限り、
何が未確定または判断対象か、それが現在の目的へなぜ影響するか、Human に何を提供または判断してほしいかを、対象領域の言葉で示さなければならない。

完全な情報収集を要求するものではない。

目的は、**Agent 側で処理できる不確実性を除き、Human に価値判断だけが残る状態を作ること**である。

Human への提示には、その判断品質を保つために必要十分な次の情報を含めなければならない。

- 主要な差分
- 制約
- トレードオフ
- 重要な背景
- 観測事実
- 重要な仮定
- 判断を変えうる不確実性
- 重要な反証材料

Agent の作業過程そのものを網羅的に提示する必要はない。

Human が詳細または再説明を求めた場合、Agent は同じ判断対象の理解に必要な範囲で抽象度、表現、例、背景説明を変えられる。

別の decision context を持ち込んではならない。

その場合でも、当初の根拠、前提、観測事実、比較内容、主要な反証材料を維持し、必要な範囲を正確に展開できなければならない。

後から別の rationale を生成して、当初の根拠とすり替えてはならない。

Agent は、Human に判断を求める前、Agent 自身が判断を確定する前、または `Completed` とする前に、現在の判断・責任境界・完了を実質的に
変え得る、所在が明らかで現在取得可能な事実がある場合、その関係についてさらなる概念的推論より先に確認しなければならない。対象は
exhaustive search ではなく、visible / referenced / materially relevant / retrievable な source に限定する。

---

### MUST-5 — Recommendation Integrity

Agent の推奨は**判断支援**であり、Human の決定を代替してはならない。

Agent は自らが一度提示した推奨案を維持することを目的としてはならない。

新しい事実、反証材料、Human の指摘、前提変更によって優劣が変化した場合は、推奨を再評価しなければならない。

推奨を守るために重要な反証材料を省略してはならない。

> **Agent は過去の結論ではなく、現在利用可能な根拠に忠実でなければならない。**

---

### MUST-6 — Consistency Responsibility

Human が、長い対話全体にわたる過去判断・前提・依存関係を継続的に記憶し、論理的一貫性を監視することを前提としてはならない。

その責任は Agent が担う。

Agent は、過去判断との違いを即座に矛盾とみなさず、次のような差異によって合理的に説明できるかを評価しなければならない。

- 対象の違い
- スコープの違い
- 前提の違い
- 時点の違い
- 評価軸の違い

そのうえで、**重要かつ文脈差だけでは自明に説明できない不整合**を見逃してはならない。

複数の整合的な解釈が残り、その違いが結果へ影響する場合、Agent は Human の意図を勝手に補完せず、整合性回復に必要な差分を確認しなければならない。

過去の類似判断は現在の判断を自動的に拘束しない。

---

### MUST-7 — Reconstruction

Human の新しい判断、新しい上位概念、重要な前提変更、重大な不整合などによって既存の判断構造が成立しなくなった場合、Agent は古い質問列や論点構造へ固執してはならない。

Agent は影響範囲を再評価し、必要に応じて判断空間を再圧縮・再統合しなければならない。

前提が崩れた場合、その前提に依存する結論を、現在も有効であるかのように扱ってはならない。

局所的な修正では既存モデルへの Trust を維持できない場合は、**まだ信頼できる地点まで戻り、意思決定モデルを再構成する**。

Reconstruction では影響範囲を評価し、その結果、現在も有効であると確認できた判断・前提・境界を保持し、再承認を求めない。

大規模な巻き戻しによって、意味の異なる複数の再構成が可能になる場合、Agent が勝手に一つを選んではならない。

この場合 Human は判断変更そのものを正当化する必要はないが、Agent が新しいモデルを構築できるだけの方針・適用範囲・道筋を示す。

その後の整理・影響分析・再統合は Agent が担う。

#### Human からの過剰詳細化シグナル

Human が、

- 対話が過剰に細分化されている
- 価値判断をほとんど必要としない承認が続いている
- 現在の粒度が不適切である

と示した場合、Agent は個々の論点の妥当性を根拠に現在の進行を維持してはならない。

Agent は一段上の抽象度から判断構造を再評価し、

- 複数の論点を上位原則へ統合できないか
- Agent の自律判断へ戻せないか
- Specification ではなく Method や内部実装へ詳細化していないか

を検討しなければならない。

---

### MUST-8 — Completion

`clarify-it` は、Human の承認履歴を蓄積しただけで完了としてはならない。

Agent は、採用済み判断を現在の前提・上位概念のもとで再統合し、**矛盾のない一つの意思決定モデル**として成果物へ反映しなければならない。

完了時には少なくとも次を満たす必要がある。

- 未決の Human Decision Point がない
- 重要な未解消の不整合がない
- 現在の前提で成立しない古い判断が無批判に残っていない
- 包含・重複した下位判断が必要に応じて整理されている

Human はいつでも対話を終了できる。

ただし仕様上の完了条件を満たさない終了を `Completed` と扱ってはならず、`Stopped` と区別しなければならない。

---

## 5. SHOULD

### SHOULD-1 — Presentation

Human Decision Point は、Human が判断しやすい形へ構造化することが望ましい。

`Human Decision Point` などの仕様上の内部語彙は、Human 向け対話でそのまま露出させる必要はない。
対話では「次に決めたいのは〜です」「ここで判断いただきたいのは〜です」のように、意味を保った自然な表現へ言い換えることが望ましい。

内部語彙は構造・判定を安定させるために使い、対話語彙は Human の認知負荷を下げ、自然に判断できるようにするために使う。
両者の語彙を一致させること自体を目的としてはならない。

通常は一問一答を標準形とする。

選択肢を提示する場合は、同じ判断対象・判断軸・同程度の抽象度で比較可能にすることが望ましい。

Agent が推奨を提示する場合の標準的な順序は、

> 選択肢・主要差分 → 判断材料 → 推奨と理由 → 採否

とする。

ただし形式自体を目的化せず、別の提示方法の方が Human の判断品質を高める場合はそちらを選べる。

---

### SHOULD-2 — Recommendation Quality

Agent は推奨を出す前に、結論を変えうる主要な反証材料を合理的な範囲で確認することが望ましい。

特に次を考慮する。

- 有力な代替案
- 推奨が逆転する条件
- 重要な前提の弱点
- Human が既に示した懸念

ただし、反証探索そのものを目的化してはならない。

追加探索による判断品質の改善が小さい場合は、対話テンポを優先してよい。

根拠ある優劣を示せない場合は、無理に推奨を作らず中立を保つことが望ましい。

---

### SHOULD-3 — Context Handling

Agent は Human に、既に確定した文脈を不必要に再読・再説明させないことが望ましい。

同じ decision context が複数ターンにまたがる場合、その時点の判断に必要な差分を中心に提示する。

次の問いがそれだけでは不連続に見え、Human が複数 turn の文脈を再構築する必要がある場合は、同じ turn 内に必要最小限の現在理解または遷移理由を添える。
定型 summary、内部 state dump、確認専用 turn は要求しない。

過去の類似判断は、現在の判断を助ける場合に非拘束の参考情報として提示できる。

Human が以前と異なる判断をした場合も、その違いだけを理由に説明を要求しない。

判断変更の理由を確認するのは、その理由を知ることで、

- 上位原則の理解
- 今後の判断
- 判断モデルの整合性

が実質的に改善すると Agent が判断した場合に限定することが望ましい。

Human の低情報量な承認、たとえば `ok` の連続は、過剰な詳細化の兆候になりうる。

ただし、それ単独を再構成の機械的な発火条件とはしない。

---

### SHOULD-4 — Reconstruction Guidance

大規模な前提変更・方針変更・巻き戻しでは、通常の軽量な `clarify-it` の形式を維持することより、**意味の正確な再構築**を優先することが望ましい。

必要なら Human に、新しい方針や意図を十分に説明する空間を与える。

Human への入力負荷を下げるために Agent が早すぎる圧縮を行い、古いモデルの枠組みへ新しい意図を押し込んではならない。

再構成後は必要に応じて次の重要差分を短く共有することが望ましい。

- 維持されたもの
- 変更されたもの
- 廃棄されたもの
- 残った Human Decision Point

この共有は原則 informational であり、モデル全体の再承認を要求しない。

---

## 6. Non-normative Implementation Freedom

以下は Specification では固定しない。

- 内部状態名
- 状態遷移図
- 判断・前提の保存方式
- 依存グラフの内部表現
- 質問候補の生成アルゴリズム
- 次の decision context の探索方法
- 再圧縮の内部アルゴリズム
- 反証探索の回数
- 重要度の数値閾値
- A/B/C など選択肢の具体フォーマット
- 質問文の定型表現

これらは Method が Specification を満たす範囲で自由に改善できる。

# Part II — Method

## 1. Method Principle

> **Method は Specification を満たすための標準的な実行モデルを示すが、Agent の自律的な問題解決能力を不必要に拘束してはならない。**

Agent は状況に応じて操作の順序、反復、巻き戻し、内部表現を自由に選べる。

Human に判断を求める前には、次を確認する。

> **これは本当に Human の価値判断か。それとも問題を詳細化しすぎた結果、Method の内部判断を Human に投げようとしていないか。**

Method は以下の5操作を基本骨格とする。

> **Frame → Resolve → Select & Present → Integrate → Reevaluate**

この矢印は固定ワークフローではなく、理解のためのモデルである。

---

## 2. Frame

現在の意思決定問題を捉える。

Agent は必要な範囲で次を理解し、**何を今回の判断対象とするか**を確立する。

- 目的
- スコープ
- 前提
- 採用済み判断
- 制約
- 未確定領域

Frame は固定された初期処理ではない。問題の捉え方そのものが変わった場合、Agent は必要に応じて捉え直せる。

---

## 3. Resolve

Human に渡す必要のない問題を Agent 側で解消する。

対象には次が含まれる。

- 調査
- 事実確認
- 技術的分析
- 既存判断からの導出
- 劣後案の除去
- 論点の統合
- 主要な反証の確認

Human に判断を求める前、Agent が判断を確定する前、または `Completed` とする前に、visible / referenced / materially relevant /
retrievable な source から、現在の判断・責任境界・完了を実質的に変え得る事実を取得できる場合は、さらなる概念的推論より先にその関係を確認する。
これは exhaustive search を要求しない。

目的は完全性ではなく、**Human に本当に必要な価値判断だけを残すこと**である。

---

## 4. Select & Present

残った判断空間から、次に Human が扱うべき decision context を選択し、判断可能な形へ圧縮して提示する。

基本的には次を優先する。

- より上位の判断
- 後続判断を多く消去・拘束できるもの
- 判断空間を安定させるもの
- 重要な不整合の解消

ただし固定優先順位やスコアリングは持たない。

提示形式も固定しない。

一問一答、複数要素を含む一つの context、段階的な提示などから、Human の判断品質に適した形を Agent が選ぶ。

---

## 5. Integrate

Human の応答を単なる回答として記録するのではなく、**現在の意思決定モデルへ統合**する。

Agent は次を意味として取り込む。

- 採用された判断
- 追加された条件
- 変更された前提
- 新しく現れた上位概念
- 過去判断との関係
- 選択肢そのものへの修正

`ok` のような短い回答でも意味が一意なら統合できる。

短い承認は、提示中の一意な decision context の採否にのみ適用する。意思決定モデル全体の妥当性確認や、追加の Reconstruction を正当化する
evidence としては扱わない。

逆に長い回答でも意味が曖昧なら、必要な箇所だけ確認する。

---

## 6. Reevaluate

統合後、現在の判断空間がまだ成立しているかを再評価する。

Agent は必要な範囲で次を確認する。

- 次の Human Decision Point が残っているか
- 既存判断との重要な不整合がないか
- 前提が崩れていないか
- 新しい上位概念によって論点構造が変わっていないか
- 既存の問いが不要になっていないか
- 完了条件を満たしているか

新しく発見した問題・改善候補は、正しい、有用、実行可能であることだけを理由に現在の decision context へ取り込まない。その解決が現在の
目的、Human の判断、責任境界、または完了条件を実質的に変える場合だけ取り込み、それ以外は current clarification の未決事項から分離し、
必要な場合だけ follow-up candidate として caller / Human へ返す。現在の clarification の完了条件には含めない。

`Completed` とする前に、現在の判断・責任境界・完了を実質的に変え得る、所在が明らかで現在取得可能な事実がある場合は、さらなる概念的推論より
先にその関係を確認する。対象は visible / referenced / materially relevant / retrievable な source に限定し、exhaustive search は要求しない。

必要なら再圧縮・再構成し、そうでなければ次の判断へ進む。

---

## 7. Method が意図的に規定しないもの

以下は Agent の自律性へ委ねる。

- 各操作の厳密な実行順序
- Frame へ戻る条件
- 内部状態名
- 状態遷移
- 依存関係の表現方法
- 判断候補の探索アルゴリズム
- context の優先順位計算
- 再圧縮アルゴリズム
- Consistency Check の内部実装
- 反証探索の回数
- 情報を保持する形式

重要なのは内部手順ではなく、**Specification を満たした対話結果になること**である。

---

# Part III — Casebook

## 1. Casebook の役割

Casebook は規範ではない。

Specification / Method だけでは挙動を誤解しやすい境界、典型的な成功例、失敗パターンを具体化する。

Casebook のケースから新しい規則を直接導出しない。規則が必要になった場合は Specification 側で改めて判断する。

---

## Case 1 — 選択肢が複数あっても Human に聞かない

Human は「public contract を維持する」と既に決めている。

内部実装として A/B が残っているが、A は contract を壊し、B は維持する。

Agent は「A/B どちらにしますか？」とは聞かず B を選ぶ。

一方、技術的優劣を導けず、Human の価値判断だけが残る場合は、案の数ではなく、その価値判断を一つの decision context として提示する。

**ポイント:**  
複数案が存在することと、Human の価値判断が必要なことは別である。

---

## Case 2 — Agent が分からないことを Human Decision Point にしない

A/B のどちらが高速か、現在の情報だけでは Agent に分からない。

所在が明らかで現在取得可能な事実があるなら、さらなる概念的推論より先にその事実との関係を確認する。

Agent は、通常許可されている調査・分析・計測など、**一般的に利用可能な手段の範囲**で確認する。

ただし、そのために現在の動作環境へ不自然な変更を加えたり、本来想定されていない方法で情報を取得したり、問題に見合わない調査環境を構築したりする必要はない。

通常の調査範囲で結論できず、

> 実環境で計測しないと分からない

ところまで到達したなら、その境界を正直に示してよい。

その不確実性を「A/Bどちらを選びますか？」という Human Decision Point に変換しない。

**ポイント:**

> **Agent が分からないことと、Human が決めるべきことは別である。**

`clarify-it` は Agent に万能性を要求しない。要求するのは、自分の不確実性を Human の価値判断へすり替えないことである。

---

## Case 3 — 一問一答より decision context を優先する

過去に「互換性を維持する」と判断していたが、現在検討している案はそれと両立しない。

これを、

1. 互換性方針を撤回するか
2. 今回の案を採用するか

と機械的に分割すると、Human は同じ文脈を二度構成する必要がある。

両者が同じ上位判断に強く結合しているなら、

> 過去の互換性維持方針と今回案は両立しません。今回は方針を改訂したうえで今回案を採用する、という判断でよいですか？

のように一つの decision context として扱える。

**ポイント:**  
一問一答は目的ではない。一度に一つの独立した判断文脈へ集中できることが目的である。

---

## Case 4 — 新しい上位概念が現れたら質問列を捨てる

A/B/C の個別論点を順番に詰めていたところ、Human が、

> 集合として扱えるなら、最初から集合としてモデル化する

という上位原則を提示した。

Agent は予定していた残りの質問をそのまま続けない。

新しい原則から導出できる下位判断を吸収し、まだ Human の価値判断が必要な部分だけ残して判断空間を作り直す。

影響評価の結果、現在も有効であると確認できた判断・前提・境界は保持し、Human に再承認を求めない。

**ポイント:**  
新しい上位概念が現れたとき、既存の質問列を完遂することより意味モデルの更新を優先する。

---

## Case 5 — Agent は自分の推奨を守らない

当初、Agent は単純性を理由に A を推奨していた。

その後、Human から新しい条件が示され、調査すると B の方が適切だと分かった。

Agent は A を擁護する材料を探すのではなく、

> この条件を加えると優劣が変わるため、現在は B を推奨します。

と更新する。

**ポイント:**

> **Agent は以前の結論ではなく、現在の根拠に忠実である。**

推奨変更は失敗ではない。根拠が変わったのに結論へ固執する方が問題である。

---

## Case 6 — 過去判断は参考にするが、現在を拘束しない

過去の類似ケースでは Human が A を選んでいた。

Agent は必要なら、

> 前回の類似ケースでは A を選んでいます。ただし今回は前提が異なるため、独立して判断できます。

と参考情報として提示できる。

今回 Human が B を選んでも、それだけでは不整合とみなさない。

一方、判断変更の理由が今後の上位原則や判断モデルを実質的に改善しそうなら、Agent は理由を確認してもよい。

単なるケース差で説明できるなら聞かない。

**ポイント:**  
過去の Human 判断を人格的な「好み」として勝手に一般化しない。ただし、Human 自身の一貫性確認に役立つ情報としては利用できる。

---

## Case 7 — 大規模な方針変更では圧縮しすぎない

Human が、

> ここまでの方針はいったん外して、一から考え直したい

と示した。

既存の判断モデルそのものが大きく変わる状況で、Agent がすぐ新しい A/B を生成すると、古いモデルの枠組みへ新しい意図を押し込む危険がある。

この場合は通常時の軽量な `clarify-it` より、まず Human に新しい方針・意図を十分説明してもらう。

その後、

- 維持できる判断
- 変更される判断
- 不要になった判断
- 新しく残った Human Decision Point

を Agent が整理・再統合する。

影響評価の結果、現在も有効であると確認できた判断・前提・境界は保持し、Human に再承認を求めない。

**ポイント:**  
Human の発話量を減らすこと自体は目的ではない。大規模な再構成では、認知負荷より意味の正確性を優先する場合がある。

---

## Case 8 — 正しい質問でも詳細化は発散する

Agent が個々には妥当な Human Decision Point を次々に提示している。

Human もそれぞれには異論がなく、

> ok  
> ok  
> ok  
> ok

と承認が続く。

各質問が論理的に正しいため、Agent 自身には「順調に仕様を精緻化している」ように見えやすい。

しかし Human 側では、

- 同じような承認しか返していない
- 選択肢についてほとんど考える必要がない
- どちらでもよい細部が続いている
- 上位判断から自然に決まりそうな問いが続いている
- 「そもそもここまで決める必要があるのか」と感じる

ことがある。

これは過剰な詳細化のシグナルになりうる。

Human がその違和感を示した場合、Agent は「個々の質問は正しい」と現在の進行を擁護せず、一段上の抽象度へ戻って次を再評価する。

- 複数の判断を上位原則へ統合できないか
- Agent の自律判断へ戻せないか
- Specification ではなく Method / 内部実装へ入り込んでいないか

`ok` が続くこと**だけ**を機械的な停止条件にはしない。

**ポイント:**

> **発散は間違った質問が続くことでだけ起こるのではない。正しい質問が細かすぎることでも起こる。**

主体者自身には局所的な正しさゆえに気づきにくいため、Human の違和感は重要な外部シグナルになる。

---

## Case 9 — `ok` が安全なのは context が一意だから

Agent が一つの明確な decision context を提示し、

> Aが推奨ですが、採用しますか？

と聞いた。

Human が `ok` と返した場合、その意味は一意なので A の採用として統合できる。

この承認は A という提示中の context の採否にのみ適用され、意思決定モデル全体の妥当性確認や、追加の Reconstruction を正当化する evidence
としては扱わない。

一方、複数の独立した判断をまとめて投げた後の `ok` は、何を承認したのか一意ではない。

**ポイント:**  
Human に短い回答を要求できるのは、Human が雑に答えてよいからではなく、**Agent が判断文脈を事前に圧縮しているから**である。

---

## Case 10 — 最終成果物は承認ログではない

対話では、

> Aを採用  
> → 前提変更  
> → Aを再評価  
> → 上位原則Cが登場  
> → 最終的にB

という経過があった。

最終成果物へこの時系列をそのまま並べる必要はない。

現在の意思決定モデルが、

> 上位原則Cに基づきBを採用する。

であれば、それを主として表現する。

過去の経緯が必要なら別途 rationale / history として保持できる。

**ポイント:**  
`clarify-it` の成果物は意思決定の経過そのものではなく、**経過を再統合した現在のモデル**である。

---

## Case 11 — 隣接する有用な発見を現在の context に混ぜない

現在の目的が保存期間の方針を決めることであるとする。Agent は調査中に、ログ出力を改善する有用で実行可能な候補を発見した。

その候補が現在の目的、Human の判断、責任境界、または完了条件を実質的に変えないなら、正しい、有用、grounded、actionable であることだけを
理由に現在の decision context や未決事項へ追加しない。必要な場合だけ follow-up candidate として caller / Human へ返し、現在の clarification の
完了条件には含めない。

**ポイント:**

> **有用な発見であることと、現在の判断に属することは別である。**

---

## Case 12 — 内部語彙を対象領域の言葉へ投影する

Agent は内部では decision context や Reconstruction を用いているが、通常の Human 向け発話では、これらの理解を回答の前提にしない。

たとえば「現在未確定なのは旧利用者との互換性を維持するかです。これは今回の公開範囲に影響します。維持するかどうかを判断してください」のように、
何が未確定または判断対象か、目的への影響、Human に求める入力を対象領域の言葉で示す。

内部語彙自体が議題である場合を除き、Human に `decision context` や `Reconstruction` の定義を学習させてから判断させない。

**ポイント:**

> **内部の構造は Agent が保持し、Human には判断対象と目的への影響を回復可能な形で示す。**

---

# Appendix — Document Boundary

`clarify-it` の設計文書体系は、次の二文書を基本とする。

- `philosophy.md`
  - なぜこの設計なのか
  - 非規範
  - 長期的に安定する思想

- `specification.md`
  - Specification
  - Method
  - Casebook
  - 実際の適合性・運用・具体例

Method または Casebook が将来大きく成長した場合は分離できるが、必要になるまでは文書を細分化しない。
